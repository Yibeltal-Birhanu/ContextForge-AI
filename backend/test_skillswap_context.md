# 1. Project Overview

## Project Summary

SkillSwap Ethiopia is a peer-to-peer web platform that enables Ethiopian users to offer skills they can teach and find skills they want to learn from other users, without monetary exchange. The MVP covers user accounts, skill-based profiles, user search and discovery, exchange requests, session scheduling, in-app notifications, and ratings/reviews. The system is delivered as a single Docker Compose stack on a cloud VPS, with a React (Vite) SPA, a Python/FastAPI REST API, PostgreSQL for persistent storage, Redis for caching and as a Celery broker, and Nginx as a reverse proxy.

## Problem

People in Ethiopia lack an accessible platform to exchange skills with peers, learn new abilities, and teach what they know without monetary barriers. SkillSwap Ethiopia removes that barrier by providing a structured way to match skill-teachers with skill-learners and to coordinate the exchange.

## Target Users

- Ethiopian users seeking to learn new skills
- Ethiopian users seeking to teach skills they know
- Peer-to-peer learners and mentors


# 2. Functional Requirements

1. FR-001: User Registration - Unregistered users can create an account using an email and password. The system hashes passwords securely, rejects duplicate or malformed emails, enforces password complexity, and auto-authenticates the user on success.
2. FR-002: User Login - Registered users can log in with email and password. The system returns a generic error on failure and establishes a session on success.
3. FR-003: User Logout - Authenticated users can end their session from any page where the action is available, after which protected pages are inaccessible until a new login.
4. FR-004: Profile Creation and Management - Users can create and edit a profile with a name, optional bio, and at least one teachable or learnable skill, and can add or remove skills from each list without duplicates.
5. FR-005: View User Profile - Users can view the public profile of any other user, including teachable skills, learnable skills, average rating, and written reviews. Users cannot edit other users' profiles.
6. FR-006: Search and Discovery - Users can search other users by a skill keyword, filter by 'teach' or 'learn', and see matching results linking to public profiles. Empty search keywords are rejected.
7. FR-007: Compatibility Indication - When viewing another user's profile, the system indicates a two-way skill match (one user offers a skill the other wants to learn and vice versa) and shows no indicator otherwise.
8. FR-008: Send Exchange Request - A user can send an exchange request specifying the skill they will teach and the skill they want to learn from the recipient, with self-requests, duplicate pending requests, and invalid skill pairs blocked. The recipient is notified.
9. FR-009: Respond to Exchange Request - A recipient can accept or decline a pending request, changing its status irreversibly. The requester is notified of the decision.
10. FR-010: View Exchange Request Status - Users can view lists of sent and received exchange requests with their current status, restricted to the respective sender or recipient.
11. FR-011: Session Scheduling - Either party of an accepted exchange can schedule a session with a future date, time, and optional notes. The session is stored with status 'scheduled' and both parties are notified.
12. FR-012: View Scheduled Sessions - Users can view all sessions they participate in, clearly labeled as upcoming or past. Sessions of non-participants are not visible.
13. FR-013: Mark Session as Completed - Either participant can mark a scheduled session as completed once its scheduled time is in the past, changing status to 'completed' and notifying both parties.
14. FR-014: Notifications - Users receive in-app notifications for received exchange requests, request acceptances and declines, session scheduling, and session completion, and can mark notifications as read.
15. FR-015: Rate Completed Session - A user can submit a 1-5 star rating for another participant of a completed session, at most one rating per session per partner, and ratings are not editable in the MVP.
16. FR-016: Write Review for Completed Session - A user can submit a free-text review (with a defined maximum length) for another participant of a completed session, at most one review per session per partner, and reviews appear on the reviewed user's profile.
17. FR-017: Display Average Rating and Reviews on Profile - A user's public profile shows their average rating to one decimal place, the total number of ratings, and a list of written reviews with associated star ratings and reviewers, with an appropriate empty state when none exist.


# 3. Non-Functional Requirements

1. NFR-001: Password Security - Passwords are stored using a salted, industry-standard hashing algorithm (bcrypt) and are never stored, logged, or transmitted in plain text; production traffic uses HTTPS.
2. NFR-002: Authentication Enforcement - All endpoints and pages accessing user data require an authenticated session except registration and login; users can only access or modify their own data.
3. NFR-003: Data Validation - All inputs are validated server-side using Pydantic (and client-side in the SPA) with clear error messages for invalid formats and missing required fields.
4. NFR-004: Search Performance - Search queries return results within 2 seconds under normal load and remain usable as the user and skill base grows within the MVP.
5. NFR-005: Notification Delivery - Notifications are generated and made available in the application within 1 minute of the triggering event under normal operation and are not duplicated for the same event.
6. NFR-006: Containerized Deployment - All services (app, database, cache, proxy) are defined in a Docker Compose configuration and start with a single command on a clean cloud VPS, with configuration via environment variables.
7. NFR-007: Data Persistence - All platform data is stored in PostgreSQL with schema-level constraints, foreign keys, and uniqueness; data survives container restarts via mounted volumes.
8. NFR-008: Caching and Background Tasks - Redis is used for caching frequent read data and as the broker for Celery background workers that handle notifications and other asynchronous work.
9. NFR-009: Usability - The UI is clear and consistent, all primary user flows are completable by a first-time user, error messages describe the problem and the corrective action, and user-facing text is in clear English.
10. NFR-010: Browser Compatibility - All core features work without errors on the latest stable versions of at least two major desktop browsers.
11. NFR-011: Availability and Reliability - Restarting containers does not cause data loss; PostgreSQL and Redis use mounted volumes for persistence.
12. NFR-012: MVP Scope Containment - The MVP excludes paid, monetary, in-app chat, video calling, or other features beyond skill discovery, matching, exchange requests, scheduling, notifications, and ratings/reviews.


# 4. Architecture

SkillSwap Ethiopia is a single-codebase web application deployed as a set of containerized services via Docker Compose. The backend is a single Python/FastAPI REST API backed by PostgreSQL for persistent storage and Redis for caching and as a Celery broker for asynchronous notification and background tasks. The frontend is a Vite-built React SPA served by an Nginx container. A reverse proxy container routes traffic to the frontend and the API. All services run in a single Docker Compose stack on a cloud VPS. The architecture deliberately avoids microservices; the MVP is a single deployable backend service plus background workers, keeping the system simple while still satisfying the notification timeliness and caching requirements through Redis-backed async workers.

# 6. Data Model

- User: Stores account credentials with fields: id (UUID, primary key), email (unique, not null), password_hash (bcrypt, not null), is_active (boolean), created_at (timestamp).
- Profile: Stores public profile information with fields: id (UUID, primary key), user_id (unique foreign key to User), display_name (not null), bio (text, nullable), created_at, updated_at.
- Skill: Stores teachable and learnable skills per profile with fields: id (UUID, primary key), profile_id (foreign key to Profile), name (not null), kind (enum 'teach' or 'learn', not null), created_at; uniqueness on (profile_id, name, kind).
- ExchangeRequest: Records a skill-exchange proposal with fields: id (UUID, primary key), requester_id (foreign key to User), recipient_id (foreign key to User), teach_skill (not null), learn_skill (not null), status (enum 'pending', 'accepted', 'declined'), created_at, responded_at (nullable); uniqueness on (requester_id, recipient_id, teach_skill, learn_skill) for pending requests.
- Session: Records a scheduled meeting with fields: id (UUID, primary key), exchange_request_id (unique foreign key to ExchangeRequest), proposed_by_id (foreign key to User), scheduled_for (timestamp, future at creation), notes (text, nullable), status (enum 'scheduled', 'completed'), created_at, completed_at (nullable).
- Notification: In-app notification with fields: id (UUID, primary key), recipient_id (foreign key to User), type (enum 'request_received', 'request_accepted', 'request_declined', 'session_scheduled', 'session_completed'), payload_json (jsonb), is_read (boolean, default false), created_at.
- Rating: Star rating on a completed session with fields: id (UUID, primary key), session_id (foreign key to Session), rater_id (foreign key to User), ratee_id (foreign key to User), stars (integer 1-5, not null), created_at; uniqueness on (session_id, rater_id).
- Review: Free-text review on a completed session with fields: id (UUID, primary key), session_id (foreign key to Session), rater_id (foreign key to User), ratee_id (foreign key to User), text (text, max length enforced), created_at; uniqueness on (session_id, rater_id).


# 7. API Contract

- POST /api/auth/register - Create a new user account and return a JWT.
- POST /api/auth/login - Authenticate with email and password and return a JWT.
- POST /api/auth/logout - Invalidate the current session (client-side token discard; optionally a server-side denylist).
- GET /api/auth/me - Return the authenticated user and basic profile information.
- GET /api/profiles/me - Return the authenticated user's profile with skills.
- PUT /api/profiles/me - Update the authenticated user's display name and bio.
- GET /api/profiles/{user_id} - Return another user's public profile including average rating and reviews.
- POST /api/profiles/me/skills - Add a teach or learn skill to the authenticated user's profile.
- DELETE /api/profiles/me/skills/{skill_id} - Remove a skill from the authenticated user's profile.
- GET /api/search/users?q={keyword}&filter={teach|learn|any} - Search users by skill keyword with optional kind filter; empty q is rejected.
- POST /api/exchange-requests - Create a new exchange request to another user with teach_skill and learn_skill.
- GET /api/exchange-requests/sent - List the authenticated user's sent exchange requests with status.
- GET /api/exchange-requests/received - List the authenticated user's received exchange requests with status.
- POST /api/exchange-requests/{id}/respond - Accept or decline a received exchange request (body: action accept|decline).
- POST /api/exchange-requests/{id}/sessions - Schedule a session for an accepted exchange request with scheduled_for and optional notes.
- GET /api/sessions - List sessions the authenticated user participates in, labeled as upcoming or past.
- POST /api/sessions/{id}/complete - Mark a scheduled session as completed (only after scheduled_for).
- GET /api/notifications - List notifications for the authenticated user.
- POST /api/notifications/{id}/read - Mark a notification as read.
- POST /api/sessions/{id}/rating - Submit a 1-5 star rating for the other participant of a completed session.
- POST /api/sessions/{id}/review - Submit a free-text review for the other participant of a completed session.


# 8. Security Requirements

- Password Storage: Use bcrypt with per-user salt for all password hashes; never store, log, or return plain-text passwords.
- Authentication: Issue short-lived JWT access tokens on login; require Authorization: Bearer <token> for all endpoints except /api/auth/register and /api/auth/login.
- Authorization: Enforce object-level ownership checks server-side so a user can only read or modify their own profile, requests, sessions, notifications, ratings, and reviews.
- Input Validation: Validate every request payload with Pydantic models, including email format, password complexity, rating range (1-5), future-dated session times, and review length; reject with clear error messages.
- Transport Security: Terminate HTTPS at the Nginx reverse proxy in production with a valid TLS certificate and redirect HTTP to HTTPS.
- Error Handling: Return generic authentication error messages on login failures and structured validation error messages elsewhere; never leak stack traces, secrets, or internal details.
- Secrets and Configuration: Provide database URL, Redis URL, JWT secret, and other environment-specific values through environment variables or an .env file outside application images.
- Rate Limiting and Abuse: Apply basic rate limiting on registration, login, and request-creation endpoints at the API or reverse proxy layer to deter abuse.
- CORS: Restrict CORS to the SPA's origin; do not allow wildcard origins in production.
- Data Isolation: Enforce that all queries are scoped to the authenticated user where required and never trust client-supplied user identifiers for ownership decisions.
